# リレーの信頼性

[English](./relay-reliability.md) | **日本語**

## タイムアウトと再試行

Node HTTP トランスポートは keep-alive を無効にし、検証済み DNS アドレスへ接続を固定します。レスポンス本文を含む要求全体の期限は45秒、ソケットのアイドル期限は35秒です。DNS 解決にも期限があります。SSE はヘッダー受信後に全体期限を解除し、アイドル期限を維持します。ライブラリでは `RelayClientSecurityOptions` の `requestTimeoutMs` と `socketTimeoutMs` を設定できます。タイムアウトのコードは `ETIMEDOUT` です。成功した DNS 固定と安全性エラーはキャッシュし、一時的な DNS 障害だけを同じ検証条件で再試行します。

ワーカーと発注側のポーリングは、一時的なネットワーク障害と HTTP 429/502/503/504 を再試行します。待機時間は125〜250ミリ秒から倍増し、ランダムな揺らぎを加えて最大15〜30秒になります。試行ごとに機密情報を含まない通知を出し、キャンセルで待機を中断できます。認証・検証・SSRF などの恒久的なエラーは即時に失敗します。HTTP 登録も同じ期限で最大5回試行します。POST が既に受理された可能性があるため、送信自体は自動再試行しません。

## 保持と受理

保持は最初の受理から始まり、`expiresAt <= now` で終了します。リース・peek・
再送は期限を延長しません。暗号化された依頼の期限は中継器から読めません。
ゲートウェイの依頼期限の既定600000ミリ秒は変わりません。依頼の保存内容は
署名された暗号文と経路の情報で、平文の依頼フィールドを追加しません。

| ライブラリ設定 | Worker バインディング | ローカル `relay start` フラグ | 既定値 |
| --- | --- | --- | --- |
| `envelopeTtlMs` | `ACP_ENVELOPE_TTL_MS` | `--envelope-ttl-ms` | 86400000ミリ秒（24時間） |
| `maxQueueSize` | `ACP_MAX_QUEUE_SIZE` | `--max-queue-size` | 宛先ごと256件 |
| `maxQueueBytesPerRecipient` | `ACP_MAX_QUEUE_BYTES` | `--max-queue-bytes` | 宛先ごと4194304バイト（JSON の UTF-8） |
| `maxEnvelopeBytes` | `ACP_MAX_ENVELOPE_BYTES` | `--max-envelope-bytes` | 262144バイト（JSON の UTF-8） |
| `maxEnvelopesPerSender` | `ACP_MAX_ENVELOPES_PER_SENDER` | `--max-envelopes-per-sender` | 選択した宛先の件数上限、通常256件。送信者・宛先の組ごと |
| `seenTtlMs` | `ACP_SEEN_TTL_MS` | — | 3600000ミリ秒。再送記録は件数も制限 |

ライブラリとローカルの値は正の整数です。不正な Worker 設定値は従来どおり
既定値に戻ります。ライブラリ・ローカルの明示値を既定値より優先し、Worker は
既存の環境変数パーサーを使います。リース中もすべての上限に含めます。
上限と等しい状態までは許可し、超える受理だけを拒否します。

宛先・全体の容量や送信者の件数による一時拒否は、次の応答です。

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json; charset=utf-8
Retry-After: 60
Cache-Control: no-store

{"error":"RELAY_RETRY_LATER","retryable":true,"retryAfterMs":60000}
```

待機ヒントは3600000ミリ秒以下の正の整数、`Retry-After` は秒単位の切り上げ
（1〜3600）です。この版は60000ミリ秒を使います。件数や依頼の内容は返しません。
拒否した封筒のキュー・再送記録・期限延長・wake 記録は追加しません。
既存の期限切れの処理は独立して行います。不正・過大な本文は恒久エラーの
HTTP 400 です。単体でも宛先のバイト上限に収まらない封筒も同じです。
`RELAY_CAPACITY` は他の既存経路用に公開エラー一覧へ残します。
WebSocket は `{"ok":false,"error":"RELAY_RETRY_LATER","retryable":true,"retryAfterMs":60000}`
を返します。既存 HTTP クライアントは `RELAY_REJECTED: 429` を返し、
送信を自動再試行しません。受信側の一時エラー処理は従来どおりです。

キュー内の ID は再送記録の期限切れ・入替後も `REPLAYED_ENVELOPE` となり、
元の内容・期限を維持します。受領確認・取得によって既存の再送記録は消えません。
キューと記憶された記録の両方がなくなった後は、無期限の再送履歴を持ちません。

Durable Object は元の数値の期限・リース・再送・アラームを再起動後も保持します。
更新は新規受理だけに適用し、既存の10分の期限を書き換え・延長しません。
クラス名・マイグレーションタグは変えません。公開中継器への反映には運用者による
Worker のデプロイ・設定更新が必要で、この変更では実施しません。ローカル・
組み込みでは更新後に新しい既定値を使います。古い保存形式を置き換える前には、
固定の待ち時間ではなく、その設定された保持期間を踏まえてキューを排出します。

## HTTP リースと受領確認

`GET /envelopes?recipient=<did>&lease=true`（`/inbox/<did>` も対応）で30秒の可視性リースを取得します。封筒はキューに残り、既存の容量制限に含まれます。未確認の封筒はリース期限後に再配信されますが、元の設定された TTL（既定24時間） は延長しません。Durable Object はリースを永続化し、再起動後も維持します。`lease=true` のない要求、SSE、WebSocket は従来どおり取得時に削除します。peek はリースを取得・延長しません。

永続化または処理後に `DELETE /envelopes/<envelopeId>?recipient=<did>` を、新しい受信者用 RelayAuth トークン（`receive` アクション）で呼び出します。削除時は204、既に存在しない場合は404を返します。HTTP クライアントは両方を成功として扱います。他の受信者のキューは読み取り・削除できません。確認してもリプレイ記録は消えず、署名・順序・時刻・認証 nonce の検証を維持します。

ランタイムの HTTP ポーリングはリースを利用します。外部の `HttpRelayClient.receive` 利用者は `{ lease: true }` で有効化し、処理後に `acknowledgeDelivery` を呼びます。クライアントは取得した封筒を検証してから受信者と封筒 ID で重複を排除します。記録期間は10分、上限は16,384件です。処理済み封筒が再配信されると確認を再試行します。重複排除領域が満杯ならエラーを返します。

`--inbox` ワーカーは受理記録に `envelopeId` を追加し、ファイルをディスクへフラッシュしてから提案を確認します。再起動時も記録済み ID によって二重追記・二重実行を防ぎます。ID のない旧記録も読めます。永続化が失敗した提案は確認しません。`--inbox` がない場合はアダプター実行成功後に確認します。セッションイベントは監査処理後、制御受領証は消費時に確認します。確認機能のないトランスポートでは従来の動作を維持します。

`--on-receive` は従来どおり永続化後のベストエフォート通知です。耐久性はフックの完了ではなく inbox が担います。外部副作用の厳密な一度だけの実行や、中断した二者間セッションの自動再開は保証しません。永続化前のクラッシュでは再配信され、永続化後は inbox が復旧元です。この変更による公開リレーの自動デプロイは行いません。
