# リレーの信頼性

[English](./relay-reliability.md) | **日本語**

## タイムアウトと再試行

Node HTTP トランスポートは keep-alive を無効にし、検証済み DNS アドレスへ接続を固定します。レスポンス本文を含む要求全体の期限は45秒、ソケットのアイドル期限は35秒です。DNS 解決にも期限があります。SSE はヘッダー受信後に全体期限を解除し、アイドル期限を維持します。ライブラリでは `RelayClientSecurityOptions` の `requestTimeoutMs` と `socketTimeoutMs` を設定できます。タイムアウトのコードは `ETIMEDOUT` です。成功した DNS 固定と安全性エラーはキャッシュし、一時的な DNS 障害だけを同じ検証条件で再試行します。

ワーカーと発注側のポーリングは、一時的なネットワーク障害と HTTP 429/502/503/504 を再試行します。待機時間は125〜250ミリ秒から倍増し、ランダムな揺らぎを加えて最大15〜30秒になります。試行ごとに機密情報を含まない通知を出し、キャンセルで待機を中断できます。認証・検証・SSRF などの恒久的なエラーは即時に失敗します。HTTP 登録も同じ期限で最大5回試行します。transport の送信単体は1回の試行です。ゲートウェイの保存済みタスク封筒は、下記の手順で同じ ID を再試行します。

## HTTP リースと受領確認

`GET /envelopes?recipient=<did>&lease=true`（`/inbox/<did>` も対応）で30秒の可視性リースを取得します。封筒はキューに残り、既存の容量制限に含まれます。未確認の封筒はリース期限後に再配信されますが、元の10分の TTL は延長しません。Durable Object はリースを永続化し、再起動後も維持します。`lease=true` のない要求、SSE、WebSocket は従来どおり取得時に削除します。peek はリースを取得・延長しません。

永続化または処理後に `DELETE /envelopes/<envelopeId>?recipient=<did>` を、新しい受信者用 RelayAuth トークン（`receive` アクション）で呼び出します。削除時は204、既に存在しない場合は404を返します。HTTP クライアントは両方を成功として扱います。他の受信者のキューは読み取り・削除できません。確認してもリプレイ記録は消えず、署名・順序・時刻・認証 nonce の検証を維持します。

ランタイムの HTTP ポーリングはリースを利用します。外部の `HttpRelayClient.receive` 利用者は `{ lease: true }` で有効化し、処理後に `acknowledgeDelivery` を呼びます。クライアントは取得した封筒を検証してから受信者と封筒 ID で重複を排除します。記録期間は10分、上限は16,384件です。処理済み封筒が再配信されると確認を再試行します。重複排除領域が満杯なら安全のため失敗します。

`--inbox` ワーカーは受理記録に `envelopeId` を追加し、ファイルをディスクへフラッシュしてから提案を確認します。再起動時も記録済み ID によって二重追記・二重実行を防ぎます。ID のない旧記録も読めます。永続化が失敗した提案は確認しません。`--inbox` がない場合はアダプター実行成功後に確認します。セッションイベントは監査処理後、制御受領証は消費時に確認します。確認機能のないトランスポートでは従来の動作を維持します。

`--on-receive` は従来どおり永続化後のベストエフォート通知です。耐久性はフックの完了ではなく inbox が担います。外部副作用の厳密な一度だけの実行や、中断した二者間セッションの自動再開は保証しません。永続化前のクラッシュでは再配信され、永続化後は inbox が復旧元です。この変更による公開リレーの自動デプロイは行いません。

## 保存済みの送信待ち

CLI worker/delegate・board・MCP ホストは、承認済みのタスク封筒を
`<data-root>/delivery/<sha256-local-signer-DID>/` に保存します。
イベントと監査エントリの両方を保存してから送信します。一時的な送信失敗では、
同じ署名済み暗号文・封筒 ID を、1分、5分、15分、その後は1時間ごとに再試行します。
検証済みの relay の待機指定があれば、さらに待ちます。relay の受理または元のタスク期限で
再試行を止めます。受理はキューへの保存であり、所有者による開封・エージェントの実行・
検収完了を示しません。`PENDING_OWNER_APPROVAL` は終端のままで、再依頼は明示操作です。

同じ署名者・データルートでゲートウェイを次回起動すると送信待ちを再開します。
停止中は再試行しません。通信の復旧は任意の双方向セッションの復元やアダプターの再実行を
意味しません。既定のワーカーのタスクジャーナルと受信記録で記録済み依頼の再実行を抑止し、
明示した inbox/audit のジャーナルパスを優先します。heartbeat と接続同意用 outbox は従来どおりです。

送信前に準備済みレコードを flush します。lease・再試行・relay 受理の管理情報は追加の flush なしでアトミックに更新し、中断後は同じ封筒 ID で再送する場合があります。変更のないレコードとディレクトリ一覧の検証を再利用し、ゲートウェイの索引更新・復元時の走査・定期削除はバッチまたはレコードごとにイベントループへ制御を返します。
並行する依頼は、署名者の送信ストアを共有し、それぞれのタスクと relay の対応を維持します。

POSIX のディレクトリ・ファイルは 0700/0600、Windows は親の DACL を継承します。
稼働中の送信は、受理の結果を取得した後に完了済みバッチの暗号文を削除します。
保守処理は期限切れの送信待ちを閉じてからメッセージ情報を削除し、残った完了・終了済み
バッチも削除します。中身を含まないメッセージ情報と
受信重複処理の記録は `max(createdAt, 元の deliveryDeadline)` の7日後まで保持します。
読み取り・再試行で期限を延ばしません。保守処理は起動時と稼働中の毎分に行い、停止中の
期限切れファイルは次回の保守まで残る場合があります。ローカル上限は送信待ち1,024通、
封筒 JSON 合計32 MiB、封筒1通256 KiB、メッセージ・受信記録は各10,000件です。
容量不足・保存失敗は固定のエラーとして報告し、未保存の送信や有効な記録の追い出しは行いません。

組み込みホストは `deliveryService` または `deliveryOptions` を注入し、
`startDelivery()`/`stopDelivery()` で稼働を制御できます。独自の transport で再起動後も
送るには固定の relay URL と resolver が必要です。名前のない注入 transport は従来の
一時的な動作です。初期化・道具の一覧・ローカル読み取りでは送信を開始せず、鍵も作りません。
transport の `send()` 単体は1回の試行のままです。この変更に relay の配備は不要で、
受理後の封筒には既存の relay の保持期間が適用されます。
[relay の動作](./relay-reliability.ja.md)も参照してください。

既存の wire スキーマが受け付ける UUID 以外の受信 ID は、導出した UUID を受信記録のファイル名に使います。署名済み記録には元の ID と封筒のダイジェストを保持します。ローカルで生成する送信 ID と保存パスは UUID のままです。

`OUTBOX_STORE_BUSY` では既存の書き込み用ロックを保持します。ローカルでロックを復旧する際は、先に書き込みプロセスが動いていないことを確認してください。試行用のリースとファイルシステムのロックは別のものです。

完了済みバッチの削除に失敗した場合は固定の保存エラーを報告し、保守処理で再試行します。relay の受理結果は維持します。
