# リレーの信頼性

[English](./relay-reliability.md) | **日本語**

## タイムアウトと再試行

Node HTTP トランスポートは keep-alive を無効にし、検証済み DNS アドレスへ接続を固定します。レスポンス本文を含む要求全体の期限は45秒、ソケットのアイドル期限は35秒です。DNS 解決にも期限があります。SSE はヘッダー受信後に全体期限を解除し、アイドル期限を維持します。ライブラリでは `RelayClientSecurityOptions` の `requestTimeoutMs` と `socketTimeoutMs` を設定できます。タイムアウトのコードは `ETIMEDOUT` です。成功した DNS 固定と安全性エラーはキャッシュし、一時的な DNS 障害だけを同じ検証条件で再試行します。

ワーカーと発注側のポーリングは、一時的なネットワーク障害と HTTP 429/502/503/504 を再試行します。待機時間は125〜250ミリ秒から倍増し、ランダムな揺らぎを加えて最大15〜30秒になります。試行ごとに機密情報を含まない通知を出し、キャンセルで待機を中断できます。認証・検証・SSRF などの恒久的なエラーは即時に失敗します。HTTP 登録も同じ期限で最大5回試行します。transport の送信単体は1回の試行です。ゲートウェイの保存済みタスク封筒は、下記の手順で同じ ID を再試行します。

## 保持と受理

401 の認証回復は既定120秒の枠全体を使い、2秒・10秒・30秒・60秒と待って、
毎回新しい時刻とキャッシュしない nonce で署名し直します。`--relay-auth-retries` の
明示指定は追加試行回数を制限し、0 は即時失敗を選びます。
常駐ワーカーは回復失敗後も unavailable のまま60秒ごとに再接続します。
認証回復を使い切ると、実行中の仕事もすべて中断として閉じ、やり直しません。未封印の監査は再実行の許可にはしません。
`--once` と依頼側は回復失敗で終了します。診断には中継器の Date と時計の差を示し、
一致時は nonce 再利用や鍵・DID の不一致も候補にします。Date がなければ差は不明です。

保持は最初の受理から始まり、`expiresAt <= now` で終了します。リース・peek・
再送は期限を延長しません。暗号化された依頼の期限は中継器から読めません。
ゲートウェイの依頼期限の既定600000ミリ秒は変わりません。依頼の保存内容は
署名された暗号文と経路の情報で、平文の依頼フィールドを追加しません。

| ライブラリ設定 | Worker バインディング | ローカル `relay start` フラグ | 既定値 |
| --- | --- | --- | --- |
| `envelopeTtlMs` | `ACP_ENVELOPE_TTL_MS` | `--envelope-ttl-ms` | 86400000ミリ秒（24時間） |
| `maxQueueSize` | `ACP_MAX_QUEUE_SIZE` | `--max-queue-size` | 宛先ごと256件 |
| `maxQueueBytesPerRecipient` | `ACP_MAX_QUEUE_BYTES` | `--max-queue-bytes` | 宛先ごと4194304バイト（JSON の UTF-8） |
| `maxEnvelopeBytes` | `ACP_MAX_ENVELOPE_BYTES` | `--max-envelope-bytes` | 262144バイト（JSON の UTF-8） |
| `maxEnvelopesPerSender` | `ACP_MAX_ENVELOPES_PER_SENDER` | `--max-envelopes-per-sender` | 選択した宛先の件数上限、通常256件。送信者・宛先の組ごと |
| `seenTtlMs` | `ACP_SEEN_TTL_MS` | — | 3600000ミリ秒。再送記録は件数も制限 |

ライブラリとローカルの値は正の整数です。不正な Worker 設定値は従来どおり
既定値に戻ります。ライブラリ・ローカルの明示値を既定値より優先し、Worker は
既存の環境変数パーサーを使います。リース中もすべての上限に含めます。
上限と等しい状態までは許可し、超える受理だけを拒否します。

宛先・全体の容量や送信者の件数による一時拒否は、次の応答です。

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json; charset=utf-8
Retry-After: 60
Cache-Control: no-store

{"error":"RELAY_RETRY_LATER","retryable":true,"retryAfterMs":60000}
```

待機ヒントは3600000ミリ秒以下の正の整数、`Retry-After` は秒単位の切り上げ
（1〜3600）です。この版は60000ミリ秒を使います。件数や依頼の内容は返しません。
拒否した封筒のキュー・再送記録・期限延長・wake 記録は追加しません。
既存の期限切れの処理は独立して行います。不正・過大な本文は恒久エラーの
HTTP 400 です。単体でも宛先のバイト上限に収まらない封筒も同じです。
`RELAY_CAPACITY` は他の既存経路用に公開エラー一覧へ残します。
WebSocket は `{"ok":false,"error":"RELAY_RETRY_LATER","retryable":true,"retryAfterMs":60000}`
を返します。既存 HTTP クライアントは `RELAY_REJECTED: 429` を返し、
送信を自動再試行しません。受信側の一時エラー処理は従来どおりです。

キュー内の ID は再送記録の期限切れ・入替後も `REPLAYED_ENVELOPE` となり、
元の内容・期限を維持します。受領確認・取得によって既存の再送記録は消えません。
キューと記憶された記録の両方がなくなった後は、無期限の再送履歴を持ちません。

Durable Object は元の数値の期限・リース・再送・アラームを再起動後も保持します。
更新は新規受理だけに適用し、既存の10分の期限を書き換え・延長しません。
クラス名・マイグレーションタグは変えません。公開中継器への反映には運用者による
Worker のデプロイ・設定更新が必要で、この変更では実施しません。ローカル・
組み込みでは更新後に新しい既定値を使います。古い保存形式を置き換える前には、
固定の待ち時間ではなく、その設定された保持期間を踏まえてキューを排出します。

## HTTP リースと受領確認

`GET /envelopes?recipient=<did>&lease=true`（`/inbox/<did>` も対応）で30秒の可視性リースを取得します。封筒はキューに残り、既存の容量制限に含まれます。未確認の封筒はリース期限後に再配信されますが、元の設定された TTL（既定24時間） は延長しません。Durable Object はリースを永続化し、再起動後も維持します。`lease=true` のない要求、SSE、WebSocket は従来どおり取得時に削除します。peek はリースを取得・延長しません。

永続化または処理後に `DELETE /envelopes/<envelopeId>?recipient=<did>` を、新しい受信者用 RelayAuth トークン（`receive` アクション）で呼び出します。削除時は204、既に存在しない場合は404を返します。HTTP クライアントは両方を成功として扱います。他の受信者のキューは読み取り・削除できません。確認してもリプレイ記録は消えず、署名・順序・時刻・認証 nonce の検証を維持します。

ランタイムの HTTP ポーリングはリースを利用します。外部の `HttpRelayClient.receive` 利用者は `{ lease: true }` で有効化し、処理後に `acknowledgeDelivery` を呼びます。クライアントは取得した封筒を検証してから受信者と封筒 ID で重複を排除します。記録期間は10分、上限は16,384件です。処理済み封筒が再配信されると確認を再試行します。重複排除領域が満杯ならエラーを返します。

`--inbox` ワーカーは受理記録に `envelopeId` を追加し、ファイルをディスクへフラッシュしてから提案を確認します。再起動時も記録済み ID によって二重追記・二重実行を防ぎます。ID のない旧記録も読めます。永続化が失敗した提案は確認しません。`--inbox` がない場合はアダプター実行成功後に確認します。セッションイベントは監査処理後、制御受領証は消費時に確認します。確認機能のないトランスポートでは従来の動作を維持します。

`--on-receive` は従来どおり永続化後のベストエフォート通知です。耐久性はフックの完了ではなく inbox が担います。外部副作用の厳密な一度だけの実行や、中断した二者間セッションの自動再開は保証しません。永続化前のクラッシュでは再配信され、永続化後は inbox が復旧元です。この変更による公開リレーの自動デプロイは行いません。

## 保存済みの送信待ち

CLI worker/delegate・board・MCP ホストは、承認済みのタスク封筒を
`<data-root>/delivery/<sha256-local-signer-DID>/` に保存します。
イベントと監査エントリの両方を保存してから送信します。一時的な送信失敗では、
同じ署名済み暗号文・封筒 ID を、1分、5分、15分、その後は1時間ごとに再試行します。
検証済みの relay の待機指定があれば、さらに待ちます。relay の受理または元のタスク期限で
再試行を止めます。受理はキューへの保存であり、所有者による開封・エージェントの実行・
検収完了を示しません。`PENDING_OWNER_APPROVAL` は終端のままで、再依頼は明示操作です。

同じ署名者・データルートでゲートウェイを次回起動すると送信待ちを再開します。
停止中は再試行しません。通信の復旧は任意の双方向セッションの復元やアダプターの再実行を
意味しません。既定のワーカーのタスクジャーナルと受信記録で記録済み依頼の再実行を抑止し、
明示した inbox/audit のジャーナルパスを優先します。heartbeat と接続同意用 outbox は従来どおりです。

C1 の永続化はゲートウェイのプロセス再起動を対象とし、送信・受領確認より前に書き込みとアトミックな置換を完了します。封筒・受信記録・既定のタスクジャーナルではファイルやディレクトリを fsync せず、電源断時の永続化は保証しません。lease・再試行・relay 受理の管理情報は、中断後に同じ封筒 ID で再送する場合があります。明示した inbox/audit のタスクジャーナルは従来の flush 方針を維持します。変更のないレコードとディレクトリ一覧の検証を再利用し、索引更新・復元時の走査・定期削除はバッチまたはレコードごとにイベントループへ制御を返します。

セッションの送信と処理済み受信記録は、準備時に署名者ロックを取得せず、一意の一時ファイルへ非同期に書き込みます。ハンドルを閉じてからアトミックに公開し、同じ署名者・relay の独立したタスクは並行して書き込めます。公開時に署名者ロックの下で容量と受信記録の状態を再確認し、ファイルシステムの再試行待機は行いません。既定のタスクジャーナルは追記ハンドルと変更のない検証済みチェックポイントを再利用し、圧縮時とワーカー停止時にハンドルを閉じます。
並行する依頼は、署名者の送信ストアを共有し、それぞれのタスクと relay の対応を維持します。

POSIX のディレクトリ・ファイルは 0700/0600、Windows は親の DACL を継承します。
稼働中の送信は、受理の結果を取得した後に完了済みバッチの暗号文を削除します。
保守処理は期限切れの送信待ちを閉じてからメッセージ情報を削除し、残った完了・終了済み
バッチも削除します。中身を含まないメッセージ情報と
受信重複処理の記録は `max(createdAt, 元の deliveryDeadline)` の7日後まで保持します。
読み取り・再試行で期限を延ばしません。保守処理は起動時と稼働中の毎分に行い、停止中の
期限切れファイルは次回の保守まで残る場合があります。ローカル上限は送信待ち1,024通、
封筒 JSON 合計32 MiB、封筒1通256 KiB、メッセージ・受信記録は各10,000件です。
容量不足・保存失敗は固定のエラーとして報告し、未保存の送信や有効な記録の追い出しは行いません。

組み込みホストは `deliveryService` または `deliveryOptions` を注入し、
`startDelivery()`/`stopDelivery()` で稼働を制御できます。独自の transport で再起動後も
送るには固定の relay URL と resolver が必要です。名前のない注入 transport は従来の
一時的な動作です。初期化・道具の一覧・ローカル読み取りでは送信を開始せず、鍵も作りません。
transport の `send()` 単体は1回の試行のままです。この変更に relay の配備は不要で、
受理後の封筒には既存の relay の保持期間が適用されます。
[relay の動作](./relay-reliability.ja.md)も参照してください。

既存の wire スキーマが受け付ける UUID 以外の受信 ID は、導出した UUID を受信記録のファイル名に使います。署名済み記録には元の ID と封筒のダイジェストを保持します。ローカルで生成する送信 ID と保存パスは UUID のままです。

`OUTBOX_STORE_BUSY` では既存の書き込み用ロックを保持します。ローカルでロックを復旧する際は、先に書き込みプロセスが動いていないことを確認してください。試行用のリースとファイルシステムのロックは別のものです。

完了済みバッチの削除に失敗した場合は固定の保存エラーを報告し、保守処理で再試行します。relay の受理結果は維持します。


`acp_delegate_task`・`acp_delegate_multi`・`acp_resubmit_pending_request` は任意の
`idempotencyKey` を受け付けます。正規化や空白除去をしない Unicode 文字列で、UTF-8 の
1〜200バイトです。例: 送信引数に `"idempotencyKey":"review-2026-11-02"` を加えます。
範囲はローカル署名者と道具の組で、MCP セッションや再起動をまたいで保持します。
同じ内容なら保留・エラーも含めた最初の結果を返し、提案と送信前承認を繰り返しません
（複数宛先では最初の宛先ごとの承認を維持します）。内容が違えば
`IDEMPOTENCY_CONFLICT` を返すため、新しい操作には新しいキーを使います。
同じサーバー内の並行呼び出しは進行中の結果を待ち、別のサーバーは有効なリース中に
`IDEMPOTENCY_IN_PROGRESS` を返します。中断後は元の ID とともに
`APPROVAL_INTERRUPTED` または `IDEMPOTENCY_RESULT_UNAVAILABLE` を返し、承認を尋ね直したり
エージェントの実行を復元したりしません。最終検収は別の判断です。
キー対応と所有者用の結果キャッシュは元のタスク期限（複数では最も遅い子の期限、作成時刻が
後ならその時刻）の7日後まで保持し、読み取りで延長しません。停止中のストアには次の保守まで
期限切れのデータが残る場合があります。期限切れキーの再利用には現在の方針を適用します。
キャッシュ参照では期限切れ招待や付け替えた別名を解決せず、relay に接続せず、保留の試行回数も
増やしません。保留の再依頼は明示操作のままで、新しい再依頼キーは現在の方針で新しい1回を
開始します。キー省略時の動作は従来どおりです。relay のデプロイは不要です。
ランタイムの単一・複数依頼も `idempotencyKey` を受け付け、キー付きの `beforePropose` は
検証済みの承認情報を返す必要があります。

C2 の操作・承認・対応・結果レコードもプロセス再起動を対象とし、書き込み完了とアトミックな公開を使います。ファイルやディレクトリを fsync せず、電源断時の永続化は保証しません。

delivery ルートには内部ファイル `.idempotency-gen` も置きます。署名者ロックの下で operation・binding の置換・削除前にサイズを1ずつ増やし、両索引はその inode・サイズとディレクトリの情報を併せて変更を判定します。ストアはこのファイルの縮小・置換を行いません。欠落・置換を検出すると両索引を作り直します。署名付きレコードの形式は変わりません。旧版はルート直下のこのファイルを無視します。旧版の変更は引き続きディレクトリの情報で検出しますが、並行する旧版どうしで同じ値になる可能性は残ります。旧版へ戻すと索引も旧版の動作になります。

ローカルキャッシュは署名者ごとに保持操作10,000件・結果 JSON 合計16 MiB、操作レコード1件4 MiBを上限とします。進行中の呼び出しは承認前に結果用の領域を予約します。容量・保存の失敗は `IDEMPOTENCY_STORE_*` の固定コードで返し、進行中の記録を削除して空けることはしません。

## 受信側の配達状態

検証済みの 0.2.0 タスクでは、対応ゲートウェイが受信側署名付きの暗号化した
`DeliveryStatus` を交換します。中身は識別子・状態・版番号・時刻だけで、
タスクの連番や双方向監査とは別経路です。版の宣言がない相手は従来の 0.1.0 の
動作を維持し、新しい封筒を受け取りません。
未接続・申請中・旧 open の相手には `received_held` と `closed` だけを返します。
最初の受け入れ時の区分をタスクに固定し、後から接続しても詳細の履歴を送りません。
接続を解除すると待機中の詳細を、ブロックすると待機中の全状態を送信対象から外します。
検査完了や内容表示だけでは開いたことになりません。接続だけの承認では元の保留依頼を
閉じ、`opened` を記録しません。

| 状態 | 記録元と意味 |
| --- | --- |
| `queued` | ローカルで承認済み暗号文を outbox に保存 |
| `relayed` | relay が受理。相手が開いたことは示さない |
| `received_held` | 受信側が隔離内容を保存。従来の認証済み保留応答もローカルの記録元になる |
| `opened` | 検査完了後、人間による契約承認を受信側が記録 |
| `handed_to_agent` | アダプターへ入力を渡す境界を受信側が記録。既読や実行完了の証明ではない |
| `replied` | 送信側が返答を検証。所有者の最終検収とは別 |
| `closed` | ローカルの期限・終了、または受信側での保留終了。未実行の証明ではない |

状態の記録は隔離内容の削除後も残り、成功した結果の後片付けは `closed` にしません。
タスク本文・検査の詳細・終了理由は含みません。既存の署名者別 delivery 保存先に
POSIX の 0600 ファイル・0700 ディレクトリと原子的な書き込みを使います
（Windows は親 DACL を継承）。状態・状態バッチ・版番号ごとの受信記録も、
C1 と同じくプロセス再起動を対象とし、書き込みを完了してから公開します。
ファイルやディレクトリを fsync せず、電源断時の永続化は保証しません。
保持期限は元のタスク期限（作成時刻が後ならその時刻）
の7日後に固定します。読み取りは期限切れを非表示にするだけで、稼働中の保守が削除します。
状態の再送は同じ封筒を使い、発生から最大24時間かつ保持期限内です。
停止中は再送も取得もしません。明示的な起動で保存済みの送信 ID の取得を再開し、
保留で依頼が終了した後も受け取れます。初期化や道具一覧では取得を始めません。
後続のローカル照会のための記録であり、新しい MCP 道具や実行・監査の保証は追加しません。
`idempotencyKey` の保存済み結果は元のメッセージ ID と封筒との対応を維持します。
受信側の状態はその元のメッセージ記録に反映され、結果の再参照では配達記録・
状態の記録・版番号ごとの受信記録を追加しません。

受信側の状態には両方のゲートウェイの対応が必要です。relay の配備は不要で、
relay の保持設定は別の変更です。

### ローカルの送信状態を読む

`idempotencyKey` 付き送信のキャッシュ再参照でも、元のメッセージ ID・タスク ID を使います。
状態照会は送信結果のキャッシュとは独立して、その ID に保存された最新の観測を返します。

`acp_message_status {"messageId":"<元の PROPOSE UUID>"}` または
`acp_message_status {"taskId":"<元のタスク ID>"}` を使い、指定は一方だけにします。
同じ署名者・データルートを使う別の入口からの送信も含め、ローカルの依頼者署名者が
送った記録を読みます。送信・更新取得・ポーリング・受信確認・配達開始・削除はしません。
タスク ID に複数の保持中の記録があれば `MESSAGE_STATUS_AMBIGUOUS` を返すため、
`messageId` で選びます。

保持期限は元の配達期限（作成時刻が後ならその時刻）の7日後に固定します。
不明な ID・別の署名者の ID・期限切れ・ローカルの鍵がない場合はすべて
`{"found":false}` です。相手が未接続でも送信記録があれば `received_held` や `closed` を
示す場合があり、記録なしは配達の結果を示しません。`updatedAt` は最後に保存した事実の
時刻です。最初の提案の再試行回数は、C1 が完了済みバッチの封筒を削除すると0になります。
読み取りはファイルを変更せず、稼働中の保守が独立して期限切れを削除します。

C4 に従い、当初未接続だった依頼の受信側詳細は、後で接続しても `received_held` と
`closed` だけです。受信側の状態は署名付きのゲートウェイの主張で、双方向監査とは別です。
引き渡しは既読や実行の証明ではありません。従来の相手では受信側状態は null です。
最初の委任結果のキャッシュや、保留の明示的な再依頼とは別の操作です。
ツールはゲートウェイ更新で利用でき、詳細な観測には相手の C4 対応が必要です。
relay の配備は不要です。
