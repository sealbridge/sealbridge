# 保留内容のライブラリ境界

[English](held-content.md)

`@acp/runtime` は `HeldRequestStore`・`HeldRequestReview`・注入用の
`HeldContentReviewProvider` を公開します。独立した4つのつながり基盤の PR4 です。

ストアは、元の暗号化済み署名付き封筒と所有者が署名したメタデータを
`<dataRoot>/quarantine/<sha256-local-owner-DID>/<id>.json` に保存します。
一覧に入力・タイトル・説明は含めません。既定のプロバイダーは `unavailable` を返し、
内容の保留を継続します。オフラインのルール検査は明示的に選ぶ別のプロバイダとして提供し、自動では設定しません。
`hold`・`inspect`・`showReviewedContent`・`discard`・`expire` はライブラリ API です。
内容の表示には、所有者・種類・内容・封筒・レポートのダイジェストに結び付いた
検査完了の受領書が必要です。表示によって実行やつながりの同意を承認することはありません。
タスクのダイジェストは `digest({manifest,input})` を使い、つながりと将来の
アプリケーション用途のダイジェストは復号した本文全体を対象にします。
検査のタイムアウトは既定で5秒です。エラー・タイムアウト・利用不能の場合は保留を継続します。

ホストが所有者の審査を承認し、送信者と所有者の委任関係と期限を検証します。
受信確認は `hold` の成功後にのみ行い、`expire` の実行予定を管理し、
ブロック時には `discardPeer`、判断後にはオファーの削除、結果送信後にはタスクの削除を
呼びます。読み取りはファイルを変更しません。保存期限は指定期限と24時間の早い方です。
上限は100件、封筒1件あたり256 KiB、封筒合計32 MiB、別途メタデータ1件あたり8 KiBです。
期限内のレコードを容量確保のために削除することはありません。
POSIX のパスには0700/0600を使い、Windows は親の DACL を継承し、ACL の検証は行いません。
アダプターの作業ディレクトリが分かる場合は `workspaceDir` を渡し、その配下への保存を拒否します。
単体 CLI は検証済みの manifest・入力・能力を、端末制御文字をエスケープした
JSON 文字列として表示します。`tasks list` は個別の保留 ID・タスク ID、`requests list` は
依頼者ごとの受付を一覧します。`tasks show ID` の表示成功時だけ、既存の保留レコードに
検査記録を保存します。表示は実行や接続同意の承認ではありません。
`tasks approve ID` / `tasks reject ID` は対話式 TTY で所有者が確認し、その終端の保留内容だけを
ローカルで閉じます。実行・終了済みセッションへの返信・次のタスクへの承認の保存は行いません。
新しいタスクを明示的に送信するか `pending resubmit ID` を使い、稼働中の対話式ワーカーで
新たな内容を確認し、所有者プロンプトで承認・拒否してください。新しい依頼は毎回確認します。
TTY がなければ limited タスクは保留です。`--auto-accept` は検査や実行承認を代替しません。
接続同意は `connections` で行います。従来の `requests approve` は検査済みの依頼に対する
接続同意の意味を維持し、実行を承認しません。`--trust trusted` は別の従来の権限付与です。
表示では提案の署名・manifest・宛先・内容ダイジェストを検証します。表示成功時に既存の
`HeldRequestReview.inspect` が v1 `HeldContentInspection` を同じ保留レコードへ署名・保存します。
レポートのダイジェストは `digest({type:'CliTaskDisplay',v:1,contentDigest})` です。
これは検証済み内容の表示記録であり、自動評価・所有者の同意ではありません。
失敗・中断では完了を記録しません。既存の記録があっても、所有者の新たな操作では内容を再表示します。
保存形式は変更しません。ライブラリの既定検査と非対話式ワーカーは利用不可のままです。


ゲートウェイは `<data-root>/delivery/<sha256-local-signer-DID>/` に送信待ちの封筒と
受信記録・既定のチェックポイントを保存します。同じ依頼の再到着はアダプターの再実行を
許可しません。検査・所有者による開封は従来の経路で必要です。審査待ちは依頼呼び出しの
終端で、outbox は再依頼しません。再試行は relay の受理または元の期限で止まり、
停止中のゲートウェイは次回起動まで待ちます。[relay の動作](../relay-reliability.ja.md)を参照してください。

### 受信側の配達状態

検証済みの 0.2.0 タスクでは、受信側署名付き `DeliveryStatus` で本文を含まない
保留・開く・アダプターへの引き渡し・終了を記録します。タスク連番・双方向監査とは別です。
未接続の相手には `received_held` と `closed` だけを返し、後の接続承認でも元の履歴を
送りません。検査・表示だけでは開かず、結果成功時の後片付けでは閉じません。
接続解除は待機中の詳細を、ブロックは待機中の全状態を送信対象から外します。
版の宣言がない相手は従来の 0.1.0 の動作です。記録は元の配達期限から7日後まで保持し、
稼働中の保守が期限切れを削除します。引き渡しは既読や実行の証明ではありません。
両ゲートウェイの対応が必要で、relay の配備は不要です。
状態の記録元・保持・動作は [relay の動作](../relay-reliability.ja.md)を参照してください。

### 明示的に選ぶルール検査

`createRuleBasedContentReviewProvider` を `@acp/runtime` と `sealbridge/sdk` から公開します。
検査関数と変更不可のルール記述子は `@acp/core` と SDK から公開します。
`new HeldRequestReview(owner, {provider: createRuleBasedContentReviewProvider(options)})`
を作り、`WorkerNode` に `heldReview` として渡します。
[SDK の例とレポート契約](../sdk.ja.md#明示的に選ぶオフラインの内容検査)も参照してください。
CLI・MCP のオプションは追加せず、表示による検査と既定の `unavailable` は変えません。

task 専用のプロバイダは封筒・proposal の認証と保留の結び付きを確認し、manifest 全体・
input・capabilities だけを固定のビルド済みの子へ、上限付き JSON と IPC で渡します。
鍵と通信用の資格情報を渡さず、環境変数は許可リストから作り、平文のファイル・ログを書かず、
ネットワーク呼び出しをしません。内容の実行・展開・再帰的な復号はせず、カーネルの
ネットワーク隔離ではありません。制限時間は既定5秒、最大45秒で、`inspectionTimeoutMs`
以下にします。中止・時間切れ・不正な結果・子の失敗・上限超過・コールバックの失敗では
完了にしません。表示のゲートも含め、エラー時は保留のままです。

サイズ・形式、見えない文字、指示表現、URLの形、秘密を求める文・秘密の典型的な形、
コード、上限付きbase64復号の先頭にある実行形式・アーカイブを検出します。既定は内容
256 KiB、深さ32、ノードとキー100,000、文字列ごとUTF-8で64 KiB、所見100件、復号合計64 KiB、
子の結果64 KiBで、上限は下げられます。固定コードによるヒューリスティックな所見で、
機微な可能性のあるパス部分を伏せ、証拠の抜粋は含めません。引用にも反応し、未対応の
表現は通ることがあります。URLや資格情報をオンラインで確認しません。

`pass`・`warn`・`block` はいずれも既存の `HeldContentInspection` v1 に
`status:'complete'` を記録します。`block` は所有者への最も強い注意で、自動的な
実行拒否は追加しません。完了は確認の資料を用意したことだけを表します。接続済みでも
その会期の人間による契約の開封操作が必要で、未接続のタスクは終端の保留です。
検査だけではアダプタの呼び出しや接続の承認は行いません。

`onReport(recordId, report)` は複製をメモリ上で渡します。保存するのは既存の
`reportDigest` だけで、レポート・実効上限・記録・所有者・kind・内容・正確な封筒を
結び付けます。新しいレポート保存先、監査イベント、承認の詳細欄は追加しません。
キャッシュ済み受領に所見はないので、再起動後に必要なら保存済み封筒と対応する context
でプロバイダを明示的に再実行します。完了受領から所見なしのレポートを作らないでください。
protocol・schema・manifest 必須欄・通信形式・保存形式を変えません。
