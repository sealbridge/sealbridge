# つながり交換（準備段階）

`@acp/core` は `ConnectionRequest`・`ConnectionAccepted`・`ConnectionAck` の型、
大きさと形式の検証、署名・署名検証を公開します。`@acp/runtime` は `ConnectionService`
と暗号化された制御封筒の関数を公開します。永続化・保留内容の検査・人による確認・通信は
呼出側が注入します。既定の接続ストアや確認プロバイダはありません。
送信前に所有者の同意を保存し、招待の初回使用では、確認した所有者 DID への結び付け、
limited の同意、承認通知の送信待ちを一度の更新で保存します。招待の保存だけでは受取側の
つながりを作りません。制御通知はタスクの実行とは独立しています。

## 制御通知の形式と永続化の条件

`packages/core/src/connection.ts` は `ConnectionRequest`・`ConnectionAccepted`
（`v: 1`, `protocolVersion: '0.2.0'`）と `ConnectionAck`（`v: 1`）の型と検証を定義します。
マニフェストの版は変えません。申し込みには署名を確認した AgentCard、Unicode のコード
ポイントで240字以内のひとこと、14日以内の期限、任意の招待・元の提案のダイジェストを含めます。
所有者とエージェントの DID が異なる場合は既存の委任署名が必要です。
申し込みと承認のダイジェストは署名を含むオブジェクト全体、招待のダイジェストは
検証済みの招待ペイロードから計算します。招待の表記を変えても同じ識別子になります。

所有者が署名した制御通知を、相手の所有者 DID 宛ての暗号化 SignedEnvelope に入れます。
申し込みの本文は `{ request: Signed<ConnectionRequest>, inviteToken? }`、承認と ACK は
それぞれの署名付きオブジェクトです。イベント名は `CONNECTION_REQUEST`・
`CONNECTION_ACCEPTED`・`CONNECTION_ACK`、経路は `taskId: 'conn_' + requestId`、
`seq: 0` です。ID は英数字・アンダースコア・ハイフンの1〜96文字です。
3種類とも worker の受信経路を使い、タスクの役割・監査の連番・契約・検収は更新しません。

`ConnectionService` は送信前（招待確認を含む）と通常の受信承認前に所有者の確認を要求します。
受信内容には注入された保留・検査の処理が必要です。検証済みの招待は発行側の同意となり、
最初の所有者 DID への結び付けと承認通知を一度に保存します。別の所有者は通常の保留です。
同じ所有者による再使用でも同意を更新しません。つながりは期限なしの limited ですが、
タスク実行の承認にはなりません。招待の期限切れ・失効は以後の引換えを止め、既存のつながりは消しません。

永続化ポートは型に記載した一括更新の条件、判断記録・招待の結び付けの保持、解除時の送信待ちの
取消しを実装します。再送は同じ署名付き通知を使います。現在のリレーは封筒 ID の重複を
受け付けないため外側の ID は新しくします。受信承認の適用と ACK をリレーの受領確認より先に保存し、
承認通知の再受信時は元の ACK を再送します。送信できなければ `CONNECTION_DELIVERY_PENDING` です。

4つの独立した基盤の PR3 です。運用上の既定値、既存ファイル、CLI/MCP の名前・フラグは
PR5 の切替まで変わりません。PR5 でストア・検査の実装、新しいコマンドと
タスクから独立した WorkerNode の受信処理を接続します。
切替の有効化前にリレーのルーティングを配備してください。
